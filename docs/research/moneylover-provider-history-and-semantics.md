# Money Lover provider history coverage and financial semantics

Research date: 2026-09-05

## Scope and evidence standard

This note separates three evidence levels:

- **Observed** means true of the checked-in first-party API response captures only. It is not a provider-wide guarantee.
- **Provisional** means a useful interpretation supported by the captures but not established as a stable contract.
- **Unknown** means production synchronization must not assume the behavior.

The primary evidence is the captured Money Lover responses in [`docs/moneylover/`](../moneylover/), the request shapes in [`docs/moneylover/README.md`](../moneylover/README.md), and the sanitized owner-authorized comparison in [`docs/moneylover/transaction-capture-summary.json`](../moneylover/transaction-capture-summary.json). Raw probe responses remain private and Git-ignored. [`docs/database-design.md`](../database-design.md) is a prior proposal derived from the original captures, not independent provider evidence.

The owner ran the comparison wizard with a fresh session after revoking the credentials exposed earlier; this investigation used only its local responses and sanitized summary. Attempts to access Money Lover's public web/help sites from this environment did not yield provider documentation (the main sites returned HTTP 403 and the help hostname did not resolve), so no citable public contract was found for these private web endpoints. That absence is a research limitation, not proof that documentation does not exist.

## Evidence matrix

| Area | Observed fact from captures | Provisional interpretation | Unknown / unsafe assumption | Synchronization implication |
| --- | --- | --- | --- | --- |
| Response status | All four captures have HTTP-style envelopes with `error=0`; transaction history is under `data.transactions`, while the other captures use `data[]`. | `error` is an application-level success indicator. | Error variants and whether HTTP success can accompany partial/truncated data. | Validate HTTP and envelope status and reject unexpected shapes; never equate HTTP 200 with complete coverage. |
| Pagination and truncation | The transaction request has no captured page/cursor parameter or response continuation metadata. Tested monthly aggregate responses contained up to 136 rows; the debts response contained 461. | The endpoints may return all rows for a requested scope, or may have an undocumented cap above or below untested volumes. | Caps, pagination controls, continuation signals, and silent truncation remain unknown because no transaction scope exceeded 136 rows or had an independent expected count. | Window history requests; record request/response counts and envelopes. Do not mark a scope complete or reconcile absence until cap and continuation behavior are verified. |
| Ordering | Captured transaction arrays are non-increasing by `displayDate`, including the three new aggregate ranges. Multiple rows share dates. | Newest accounting date is the observed default order. | Stable ordering within a date, ordering under larger responses, and whether new/edited rows shift boundaries. | Do not use response order as identity or a cursor. Persist source IDs and request windows; tolerate reordering and duplicates. |
| Wallet selection | Across June, July, and September probes, `walletId: "all"` returned 136/132/23 unique rows while the unions of per-wallet requests returned 138/134/24. The five missing rows all belonged to wallets marked `exclude_total=true`; no per-wallet response returned another wallet's rows. | `"all"` is a Money Lover reporting scope that excludes at least some `exclude_total` wallets, not an ingestion scope. | Whether it has other exclusion rules, including archived/deleted wallets, and whether empty tested wallets would also be omitted when populated. | Never use `"all"` for authoritative import. Enumerate wallets and request every wallet individually, including `exclude_total` and archived wallets. |
| Date-window boundaries | A request from `2026-09-01T00:00:00+07:00` through `2026-09-04T23:59:59+07:00` returns rows on all four calendar dates. The envelope echoes `2026-09-01` and `2026-09-04`. | Both endpoints may treat this request form as inclusive local calendar days. | Exact start/end inclusivity, sub-second behavior, server timezone, daylight-saving behavior outside Vietnam, and treatment of backdated/future-dated records. | CashLens should use internal half-open windows but adapt requests to demonstrated provider boundaries. Adjacent windows must overlap until duplicate/gap probes prove a safe convention. |
| `displayDate` | Every captured row encodes midnight UTC. `createdAt` can be before or after that midnight. | `displayDate` likely represents an accounting calendar date serialized as a timestamp, not the actual event instant. | Whether all clients/accounts/timezones follow this rule and whether changing timezone changes the encoded day. | Preserve the original timestamp and derive an accounting date provisionally. Do not use `createdAt` as the reporting day. |
| Source ID scope | The per-wallet probes returned 296 unique IDs across three non-overlapping ranges with no duplicates across wallets/ranges. Six of those IDs also occurred in the 461-row debts response. | IDs appear stable across these two endpoint projections and unique across the tested wallets, but connection-global scope is not yet proven. | Stability after wallet/date moves, ID reuse, and whether transfer legs have separate IDs. | Preserve opaque IDs and endpoint provenance. Before enforcing connection-global uniqueness, run the wallet-move probe; quarantine incompatible same-ID records. |
| Wallet/account references | Every captured transaction embeds one captured wallet ID and matching `currency_id=4`. All eight wallet balances use a `VND` key. | For this account, source currency ID 4 maps to VND. | General currency-ID mapping, multi-currency balance-array behavior, currency changes, and whether a transaction can differ from its wallet currency. | Resolve currency from verified wallet data, store source currency ID plus code, and group reports by code. Never hard-code `4 -> VND` globally or add unlike currencies. |
| Category identity | The category capture has 711 rows but only 145 distinct `_id` values; all 711 `(account, _id)` pairs are distinct. Parent references resolve within a wallet. | Category IDs are templates or wallet-local identities. | Whether IDs can ever be connection-global, how category moves/merges behave, and the meaning of `group`, `exclude_accounts`, and embedded `categories`. | Key normalized categories by connection, wallet, and source ID. Preserve unknown category fields without applying filtering semantics. |
| Category direction and markers | Captured ordinary type 1 rows are inflows and type 2 rows are outflows. Transfer and debt marker/type pairs are internally consistent. Four debt category IDs are absent from the category catalog. | Embedded category snapshots carry the transaction's historical classification; catalog rows describe current wallet taxonomy. | Full marker vocabulary and semantics, marker changes over time, and precedence when embedded and catalog records conflict. | Preserve embedded category data. Use a versioned allowlist for reporting; unknown or contradictory combinations are excluded with a visible warning, not silently classified. |
| Endpoint overlap and precedence | Six IDs occur in both per-wallet history and debts. Shared values mostly agree, but every overlapping row has a different category `_id`; the history category resolves in the current wallet catalog while the debts category does not. Two `parent` values normalize from history objects to the same debts ID strings, and all six `lastEditBy` values change object/string shape. | `/transaction/debts` is a specialized historical debt projection; wallet history is better aligned with current catalog identity, while debts preserves debt-specific relationship evidence. | Provider-intended category precedence, sparse-field clearing, and behavior for other overlap variants. | Stage both variants. For overlapping IDs, retain both raw versions, normalize parent/editor shapes, use wallet-history category identity for current catalog reporting, and preserve debts category/relationship evidence without overwriting blindly. |
| Transfer relationships | Two outgoing-transfer rows have `related` IDs absent from the selected wallet/date capture. | `related` likely points to another transfer leg, potentially in another wallet or outside the selected window. | Reciprocity, missing-leg behavior, fees, cross-currency transfers, deleted legs, and same-wallet transfers. | Store unresolved related IDs; never fabricate a balancing leg or require equal nominal amounts. Exclude verified transfers from income/expense while retaining wallet cash movement. |
| Debt relationships | All 275 captured `parent` references resolve in the debt capture, remain within one wallet/currency, and pair borrowing→repayment or loan→collection. | `parent` links settlement rows to a principal in this account. | Cross-wallet/currency debt behavior, restructuring, interest, write-offs, and deleted principals. | Preserve principal/settlement evidence in the transaction mirror. Debt dashboards remain deferred; unresolved links must not block ingestion. |
| Edits and deletions | Wallets expose `updateAt` and `isDelete`; captured categories/transactions show no update timestamp or tombstone. `createdAt` and `displayDate` differ. | Re-fetching overlapping/full scopes is required to discover old edits. Wallet `updateAt` is not a transaction cursor. | Old-edit visibility, deletion feed/semantics, whether absence is authoritative, wallet-move behavior, and how deleted transfer/debt links appear. | Upsert re-fetched records. Do not tombstone transactions/categories from absence until a completed authoritative-scope contract is demonstrated. Keep prior accepted data on failures. |

## What CashLens can safely promise now

1. **Lossless, retry-safe ingestion of observed shapes**, with opaque source IDs, exact decimal money, raw source evidence, endpoint provenance, unresolved references, and quarantine for malformed/contradictory records.
2. **Progressive attempted coverage**, reported per individually requested wallet and date window. `walletId: "all"` is explicitly unsuitable for import because it omitted tested `exclude_total` wallet records. CashLens may say what it requested, received, accepted, and rejected; it cannot yet claim complete Money Lover history.
3. **Conservative financial reporting**: group by currency and accounting date; include only reviewed category semantics in income/expense; exclude verified transfers and debt movements from ordinary spending while retaining them as wallet cash movements.
4. **Observed current balances**, timestamped when CashLens receives them. They are not historical end-of-day balances and need not reconcile to imported movement history.
5. **Non-destructive refreshes**. Old records may be updated when seen again, but missing rows are not proof of deletion.

CashLens cannot safely promise exact Money Lover report parity, complete history, deletion reconciliation, real-time old-edit detection, stable transfer pairing, or a provider-derived historical balance curve from current evidence.

## Owner-assisted probe pack and status

A person with legitimate account access must run these through their own browser session or a purpose-built diagnostic that redacts authorization headers, cookies, private notes, names, IDs, and amounts before sharing results. Record request parameters, HTTP status, envelope metadata, row count, ordered hashes/anonymous stable labels, and whether each expected boundary record appears. Never put tokens in URLs, logs, fixtures, issues, or the probe output.

Completed on 2026-09-05: aggregate-versus-per-wallet comparison across three ranges, and a partial endpoint-overlap comparison. The remaining boundary, cap, mutation, deletion, transfer, currency, category, and failure probes are still evidence gates for stronger provider guarantees.

| Probe | Procedure | Decision unlocked / pass condition |
| --- | --- | --- |
| Window boundary | Create or identify records exactly on start day, end day, adjacent days, and around local midnight. Query one broad window and two adjacent windows. Repeat with end times `23:59:59`, `23:59:59.999`, and next-day `00:00:00` where accepted. | Establish request inclusivity and a no-gap overlap/deduplication rule; verify how local accounting dates map to `displayDate`. |
| High-volume/cap | Query a wallet/window known to exceed 20, 100, 500, and preferably 1,000 rows; inspect network requests for continuation parameters and compare against the Money Lover UI/export count. | Identify cap, pagination mechanism, termination signal, and ordering stability. No completeness claim until every row is recoverable repeatedly. |
| Ordering mutation | Capture two identical high-volume requests, then add and edit records sharing an existing `displayDate`; capture again. | Determine whether order is stable enough for paging and prove that CashLens must not use position as a cursor. |
| Endpoint overlap | For known debt principal and settlement records, query the matching wallet/date history and debts endpoint. Compare anonymized stable IDs and field-presence hashes. | Establish overlap and field precedence without exposing payload contents. |
| Wallet/date move and ID scope | Capture one test transaction, move it to another wallet and then another date in Money Lover, capturing both source and destination scopes after each step. | Determine ID stability/global scope and whether the old scope emits a tombstone or only absence. |
| Old edit | Capture an old test transaction, edit amount/category/note, then query a recent window and a window covering that old date. | Establish how old edits become observable and set an honest refresh/reconciliation SLA. |
| Deletion and reappearance | Delete a disposable test transaction, inspect all relevant scopes/endpoints, then restore it if Money Lover supports restoration. | Determine whether there is an explicit tombstone and whether absence can ever be authoritative. This probe does **not** authorize CashLens deletion logic. |
| Transfer | Create same-currency and, if supported, cross-currency transfers; query both wallets and windows. Then edit/delete one transfer. | Establish `related` reciprocity, leg amounts, fee representation, and missing/deleted-leg behavior. |
| Currency | Capture wallets for at least two known currency codes and, if supported, a currency change or multi-currency balance. | Build a validated currency-ID/code mapping and define contradiction handling. |
| Category semantics | Create test transactions using every special category available in the UI; capture embedded/category-list marker, type, UI report inclusion, and wallet-balance effect. | Approve a versioned marker classification table; all untested markers stay unknown. |
| Failure responses | Safely exercise expired/invalid token, malformed dates, unknown wallet, oversized range, and throttling only if naturally encountered. Do not deliberately load-test. | Catalog sanitized error codes, retryability, authentication handling, and rate-limit signals. |

## Decisions and prerequisites

- The next synchronization decision can proceed conservatively by treating coverage as **attempted**, not complete, and by prohibiting absence-based deletion.
- Exact full-history and deletion guarantees require the owner-assisted probe pack above. It is a prerequisite before production synchronization can be labelled complete or authoritative.
- A connection-global transaction uniqueness constraint should remain conditional until the wallet-move/ID-scope probe passes. An implementation can initially retain endpoint/wallet provenance in staging so the key can be corrected without data loss.
- Transfer and debt links are optional, unresolved relationships during ingestion. Financial reporting must disclose excluded/unknown records rather than infer missing legs or settlements.
- No official provider contract was found; observed behavior is versioned capture evidence only. Future provider changes must be treated as contract changes and re-probed.
